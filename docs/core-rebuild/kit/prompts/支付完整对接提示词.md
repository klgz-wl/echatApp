# 支付完整对接提示词

> 用法：把本文件全文交给实现支付接入的 Agent，并同时提供目标 Android 工程目录。提示词中的尖括号参数优先从目标项目现有配置、`.core-scaffold/project.json`、接口文档和 BuildConfig 中读取；只有确实缺失且会改变实现的参数才集中询问一次。

---

你是一名资深 Android 支付工程师。请在目标 Android App 中完整接入 Core 支付脚手架，并直接完成代码、宿主集成、测试、构建和验证。不要只给方案，不要停留在 DTO 或参考类复制阶段。

本任务的完成标准是：真实运行的付费入口只使用 Core 支付状态机，能在进程死亡、配置变化、网络超时、Google Play pending、第三方页面关闭、应用切前后台后安全恢复；不会重复建单、串单、本地发币、提前记成功或重复统计收入。

## 0. 执行原则

1. 先阅读目标仓库的 `AGENTS.md`、Gradle 配置、Application、Activity、登录/会话、钱包、现有支付代码、测试以及 Core scaffold。
2. 如果目标已有 `.core-scaffold/project.json`，沿用里面已确认的 namespace、模块、存储前缀和环境，不重复询问。
3. 只补问真正缺失的项目变量。接口路径、请求字段和状态判断以本文锁定契约为准，不自行改名、增删或猜测。
4. 已有 App 必须采用 existing-project 集成：保留 UI、导航、登录身份、Git 历史和业务功能，把支付能力接入 Core；不要用示例宿主替换现有 App。
5. 先定位真实运行入口。复制进 `:core` 但没有被 App 调用的类不算完成。
6. 不允许两套支付 owner 同时运行。迁移完成后删除或彻底停用旧的 App BillingClient、旧支付 Controller、旧轮询、旧订单恢复和旧支付事件队列。
7. 使用 TDD：每项行为先写会失败的测试，再实现到通过。完成后必须执行完整测试、构建和 lint。
8. 不修改只读 reference 或伪造 platform evidence 来让验证通过。

## 2. 模块与单一责任边界

### Core 负责

- 支付 DTO、API、Repository。
- 业务订单创建。
- 支付渠道初始化与严格校验。
- 持久化支付状态机。
- Google Play 商品查询、购买请求关联、pending/recovery registry。
- 第三方支付轮询、关闭核对、超时和恢复。
- client-events 持久化有界重试。
- 钱包余额、商品和流水刷新。
- 会话归属、并发、幂等、旧结果隔离。

### App 负责

- BuildConfig/Hilt 配置注入。
- `@HiltAndroidApp` Application、`@AndroidEntryPoint` Activity。
- Activity 生命周期转发。
- Compose/ViewModel 状态映射。
- WebView 或外部浏览器展示。
- 用户可见的 loading/error/pending/success 文案。
- 支付成功后的页面刷新和展示，但不能本地增加余额。

真实运行入口必须是：

```text
UI/ViewModel
  -> PurchaseRouter
  -> PaymentCoordinator / PaymentEngine
  -> WalletRepository / PaymentRepository / Core Billing owner
```

不得再存在第二套可变支付状态机。

## 3. 鉴权与会话契约

所有业务订单、支付初始化、查单和 client-events 都使用当前 App JWT：

```http
Authorization: Bearer <App JWT>
Content-Type: application/json
```

JWT 必须属于当前用户、当前 App 和 Android 平台。payment-service 会校验订单归属。

会话至少包含：

```text
token
refreshToken
userId
epoch
revision
```

实现要求：

1. 复用宿主现有的安装 ID、登录会话和持久化存储，不创建第二个互不感知的登录 owner。
2. Core 支付前台恢复和每次购买前，先从宿主权威存储同步会话。
3. 同一会话刷新只增加 revision；重新登录生成新 epoch。
4. 所有异步支付结果必须验证 `session.epoch` 和用户归属，旧 epoch 的响应不得更新新用户 UI。
5. Core refresh 写回宿主存储必须使用跨实例原子 compare-and-set；不能用 `read -> check -> write` 的非原子序列覆盖宿主刚刷新的 token。
6. Core 支付失效不能擅自删除宿主权威登录。登出/清账号由宿主统一负责。
7. 不记录 access token、refresh token、purchase token、完整支付 URL 或原始敏感响应。


字段类型：

| JSON 字段 | 类型 | 必须说明 |
| --- | --- | --- |
| `id` | string | 业务商品 ID，必须非空 |
| `type` | string | 本充值场景必须匹配 `diamond` |
| `name` | string | 展示名 |
| `description` | string nullable | 服务端展示说明；空值不伪造本地有效期 |
| `price` | decimal/number | catalog 报价，不等于最终 Play 实付凭据 |
| `currency` | string | ISO 4217，例如 `USD` |
| `value` | integer/long nullable | 基础币数量 |
| `bonus_value` | integer/long nullable | 常规赠送 |
| `first_buy_bonus_value` | integer/long nullable | 首购赠送 |
| `original_price` | number nullable | 对比价 |
| `first_buy_price` | number nullable | 首购价 |
| `discount_rate` | number nullable | 常规折扣率 |
| `first_buy_discount` | number nullable | 首购折扣率 |
| `icon` | string nullable | 商品图标 URL |
| `is_first_buy_promotion` | boolean | 首购资格仍需结合服务端用户状态 |
| `is_promotion` | boolean | 是否普通促销 |
| `is_subscription` | boolean | 钻石充值应为 false |
| `promotion_type` | string nullable | 促销类型 |
| `sort_order` | integer | 升序排列；同序按 ID 稳定排序 |
| `tags` | string nullable | 展示标签 |
| `third_party_product_id` | string nullable | 第三方商品映射，仅作后端/兼容字段 |
| `google_product_id` | string nullable | Google Play SKU |
| `vip_level` | integer | VIP 商品等级；钻石包通常为 0 |

`payment_providers` 字段：

| JSON 字段 | 类型 | 说明 |
| --- | --- | --- |
| `priority` | integer | 仅用于展示/诊断排序 |
| `provider_code` | string | Provider 编码 |
| `provider_name` | string | Provider 展示名 |
| `supported_platforms` | string[] | 支持的平台 |

`user_info` 可空；存在时精确解析：

| JSON 字段 | 类型 | 说明 |
| --- | --- | --- |
| `current_diamond` | integer | 商品页余额快照 |
| `has_made_first_purchase` | boolean | 是否已首购 |
| `is_vip` | boolean | 是否 VIP |

首购展示资格必须同时满足 `user_info.has_made_first_purchase=false` 和 `product.is_first_buy_promotion=true`。符合资格时使用正数 `first_buy_price`，奖励为 `bonus_value + first_buy_bonus_value`；否则使用 `price` 和普通 `bonus_value`。

## 5. payment-service API 契约

支付 API base URL：

```text
<PAYMENT_BASE_URL>
示例：https://test.appjoly.com/payment-api/v1/
```

payment-service 响应是独立 envelope：

```json
{
  "data": {},
  "code": 0
}
```

`code` 可能缺省；当 `code` 存在时只有 `0` 才成功。不要强制复用业务 API 必填 `code` 的 DTO。

### 5.1 初始化支付渠道

```http
POST client/payments/initialize
Authorization: Bearer <App JWT>
Content-Type: application/json
```

请求体只能包含：

```json
{
  "order_id": "business-order-id"
}
```

严禁额外传入：

```text
country
ip
amount
currency
product_id
payment_method
merchantNo
callbackURL
returnURL
failURL
sign
```

#### 官方渠道响应

```json
{
  "data": {
    "order_id": "business-order-id",
    "channel_type": "official",
    "channel_code": "google_play",
    "open_mode": "sdk",
    "sdk_params": {
      "product_id": "play.pack.100"
    }
  }
}
```

必须同时满足：

- `order_id` 等于本次业务订单。
- `channel_type == "official"`。
- `channel_code == "google_play"`。
- `open_mode == "sdk"`。
- `sdk_params.product_id` 非空。

任何一项不满足都视为非法响应，不得拉起 Google Play。

#### 第三方渠道响应

```json
{
  "data": {
    "order_id": "business-order-id",
    "channel_type": "third_party",
    "channel_code": "payu_web_us",
    "open_mode": "webview",
    "payment_url": "https://checkout.example.com/pay",
    "expires_at": "2026-09-25T08:00:00Z",
    "query_interval_seconds": 10,
    "max_query_seconds": 600
  }
}
```

必须同时满足：

- `order_id` 等于本次业务订单。
- `channel_type == "third_party"`。
- `channel_code` 非空。
- `open_mode` 只能是 `webview` 或 `external_browser`。
- `payment_url` 必须是 HTTPS、host 非空、不能包含 URL user-info。
- `expires_at` 必须是合法 ISO8601 且晚于当前时间。
- 服务端轮询间隔必须被本地配置限制，不能小于本地最小间隔。
- `max_query_seconds` 必须被本地 `PAYMENT_POLL_MAX_SECONDS` 封顶，服务端不能延长本地 10 分钟上限。

### 5.2 查询支付状态

```http
GET client/payments/{urlEncode(order_id)}/status
Authorization: Bearer <App JWT>
```

最小响应模型：

```json
{
  "data": {
    "order_id": "business-order-id",
    "status": "pending",
    "fulfillment_status": "pending"
  }
}
```

每次响应必须先校验 `response.order_id == requested.order_id`，不匹配立即拒绝，不能更新当前 UI。

状态判断只能使用以下规则：

| 条件 | 客户端结果 |
| --- | --- |
| `status=paid && fulfillment_status=fulfilled` | 唯一成功条件 |
| `status=paid && fulfillment_status!=fulfilled` | 等待服务端发货，继续轮询 |
| `status=pending` | 继续轮询 |
| `status=failed` | 终态失败 |
| `status=cancelled` | 终态取消 |
| `status=expired` | 终态过期 |
| 其他值 | `UNCERTAIN/verification_failed`，不能判成功 |

官方 Google Play 和第三方渠道都必须通过此接口确认最终成功。充值 WebSocket/推送只能加速查单，不能替代权威状态接口。

### 5.3 上报第三方支付事件

```http
POST client/payments/{urlEncode(order_id)}/client-events
Authorization: Bearer <App JWT>
Content-Type: application/json
```

使用以下 Core 请求字段；可空字段为空时省略或传 null，不添加敏感内容：

```json
{
  "event_type": "page_loaded",
  "channel_code": "payu_web_us",
  "open_mode": "webview",
  "page": "recharge_paywall",
  "occurred_at": "2026-09-25T00:00:00.000Z",
  "opened_at": "2026-09-24T23:59:30.000Z",
  "closed_at": null,
  "duration_ms": 30000,
  "error_code": null,
  "metadata": {
    "source": "main",
    "product_id": "pack_100"
  }
}
```

Core 支持的事件：

```text
link_ok
link_error
page_opened
page_loaded
page_load_error
paid_while_open
paid_on_close
user_cancel
timeout_cancel
poll_timeout
```

响应：

```json
{
  "data": {
    "recorded": true
  }
}
```

只有 `recorded=true` 才认为上报成功。

事件实现要求：

- 独立于交易主状态，事件失败不能改变支付结果。
- 按 `userId + orderId` 归属。
- SharedPreferences/数据库持久化队列。
- 队列上限 100、最多尝试 3 次、重试间隔 5000ms，均从配置读取。
- 写入必须检查 commit/事务结果；存储失败不能假装成功。
- consumer 的单次 HTTP 或存储异常不能杀死 worker。
- 不上传完整支付 URL、URL query、HTML、表单数据、token 或 purchase token。

## 6. 初始化错误处理

只对白名单错误做业务分支，未知错误不得直接显示到 UI：

| HTTP | error | 行为 |
| --- | --- | --- |
| 400 | `order_id is required` / `invalid request` | 契约失败，不重试同一错误请求 |
| 401 | `missing authorization token` / `invalid authorization token` | 让宿主权威会话刷新；保持订单，不重复建单 |
| 403 | `payment order forbidden` | 标记 `ACCESS_DENIED`，当前客户端停止使用该订单 |
| 404 | `payment order not found` | 终态初始化失败；只有用户明确发起下一笔时才可新建订单 |
| 409 | `PAYMENT_INITIALIZATION_IN_PROGRESS` | 保留同一订单，稍后重试 initialize，绝不重新建单 |
| 409 | `PAYMENT_ORDER_NOT_INITIALIZABLE` | 当前订单不可继续；只有明确新购才新建订单 |
| 503 | `PAYMENT_CHANNEL_UNAVAILABLE` | 有明确 catalog `google_product_id` 时可复用同一业务订单构造官方兜底；没有 SKU 时提示暂不可用，不能退回业务商品 ID |
| 500 | `payment initialization failed` | 保留已创建订单并允许重试 initialize |

不要通过字符串模糊匹配任意异常决定支付路由；同时判断 HTTP 状态和白名单 error。

## 7. PaymentEngine 持久状态机

支付记录必须在调用创建订单 API 之前先持久化。建议持久模型至少包含：

```text
key
userId
productId
source
orderId
initialized route
stage
openedAt
deadline
successShownAt
successAcknowledged
error
quotePrice
quoteCurrency
quoteSource
obfuscatedAccountId
obfuscatedProfileId
officialFallbackProductId
```

状态至少包含：

```text
CREATING
INITIALIZING
OFFICIAL_READY
OFFICIAL_LAUNCHED
OFFICIAL_CONSUMED        # 仅旧客户端消费模式兼容；SERVICE 后端托管模式不进入
CHECKOUT
VERIFYING
AWAITING_FULFILLMENT
UNCERTAIN
CLOSED
TIMED_OUT
FAILED
SUCCESS
ACCESS_DENIED
```

关键规则：

1. 持久化失败时禁止调用建单、initialize 或 Billing。
2. 创建订单请求超时且没有 order ID 时标记 `UNCERTAIN/order_unknown`。同一用户存在任何 unresolved 记录时禁止创建其他商品订单。
3. initialize 失败但已有 order ID 时，重试只调用 initialize，不重新建单。
4. 商品切换不能清除、取消或覆盖 active/unresolved 记录；UI 必须禁用商品选择。
5. `OFFICIAL_READY` 指令只能 claim 一次；进程恢复不能自动重复拉起付款，需用户明确重试。
6. claim 官方指令时立即持久化 `OFFICIAL_LAUNCHED`、openedAt 和 deadline，避免进程死在 Play UI 时丢恢复窗口。
7. 每个恢复出的 payment key 在本次前台至少做一次权威核对；不能让前台循环先读空 state 后永久跳过 CLOSED/TIMED_OUT。
8. 用户关闭第三方页面时立即做最终状态查询：成功则 `paid_on_close`，否则 `user_cancel/CLOSED`。
9. 轮询超时保留原订单，不自动创建新单。晚到的 `paid + fulfilled` 仍可把原单推进 SUCCESS。
10. `SUCCESS` 先展示，再按 `PAYMENT_SUCCESS_DISPLAY_MS` 调 shown/acknowledge。延迟确认旧成功时，只有当前 UI 仍显示同一个 key 才可清空；不能清掉已经开始的新订单。
11. 支付记录必须按 userId 隔离；切账号后不能显示、查询或确认旧账号订单。

## 8. Google Play 官方支付

使用 Google Play Billing Library `9.1.0`：

- Application 级唯一 BillingClient。
- `enablePendingPurchases` 开启 one-time products。
- 启用自动服务重连。
- 每次支付前查询本次 `sdk_params.product_id` 的最新 ProductDetails。
- 不使用 catalog SKU 覆盖 initialize 返回的 SKU。
- 保存并使用一次性商品的 offerToken（如果返回）。
- 只从 Activity 拉起 BillingFlow。
- BillingClient 未 ready 时不得执行排队的查询/购买操作。
- 全进程同一时刻只允许一笔购买请求。

BillingFlowParams：

```text
productId = initialize.sdk_params.product_id
obfuscatedAccountId = create-order.obfuscated_account_id
obfuscatedProfileId = create-order.obfuscated_profile_id
```

购买关联记录必须持久化：

```text
productId
productType
purchaseToken nullable
ownerUserId          # 原始真实用户
businessOrderId      # 原始业务订单
obfuscatedAccountId  # Play 关联
obfuscatedProfileId  # Play 关联
```

匹配优先级：purchaseToken > obfuscatedProfileId > 唯一 SKU。相同 SKU 存在多笔未决记录时，不能只按 SKU 猜测。

### 后端托管 fulfillment 强制规则

```text
BACKEND_OWNS_FULFILLMENT=true
```

- 客户端不 acknowledge。
- 客户端不 consume。
- 客户端不本地加币/开通权益。
- Play `PURCHASED` 只表示 `pending/play_accepted`。
- Play `PENDING` 保持 pending，不判失败。
- 在查询到 ProductDetails 后、拉起 Play 前，持久保存真实 Play price/currency，`quoteSource=google_play`。
- 购买接受后开始查询 payment-service status。
- 只有业务订单 `paid + fulfilled` 时上报一次 success/revenue、刷新余额/商品/流水。
- 进程恢复购买时，按 raw ownerUserId 判断归属，并用 businessOrderId 查 payment-service；不要用 obfuscated 值查业务订单。

不要把 Play 回调 success、客户端 consume 完成或 purchaseToken 存在当作钱包到账成功。

## 9. 第三方支付 UI

### WebView

- 仅加载已校验的 HTTPS payment URL。
- JavaScript 按收银台要求开启。
- `allowFileAccess=false`。
- `allowContentAccess=false`。
- `mixedContentMode=NEVER_ALLOW`。
- 导航到非 HTTPS URL 时阻止并上报 `page_load_error`。
- 释放时 stopLoading + destroy。
- Back 和关闭按钮都进入 Core close 流程，不能直接丢弃订单。

### 外部浏览器

- 使用 `ACTION_VIEW` 打开。
- 打开失败上报 page_load_error，并让 Core 收口当前 checkout。
- App 回到前台立即查单。
- 浏览器关闭不可可靠感知时，依靠前台查单和持久化 deadline，不创建新单。

WebView/浏览器只是展示层，不得拥有独立轮询、订单状态机或成功判断。

## 10. UI 状态与交互

付费页必须有：

```text

retryable error
empty
catalog success
preparing
official launching
Play pending
third-party waiting
awaiting fulfillment
cancelled
timed out
failed
success
```

要求：

- 不能在 catalog 失败时回退假商品或本地固定价格。
- active/unresolved 支付期间商品卡必须真实 disabled，包含点击、语义和无障碍状态。
- 错误只显示资源化、安全文案，不显示原始 JSON、trace、HTTP body、Google debugMessage 或内部 error code。
- success 后刷新商品、余额和最近流水；刷新失败不能把已确认成功改成失败。
- 所有屏幕使用同一个权威余额源。
- Activity/配置变化不取消订单创建、initialize、Billing 关联或轮询。

## 12. 埋点和收入

支付事件至少包含：

```text
status
af_success
pay_method
payment_flow
entry_source
package_id
af_order_id
stage
af_content_id（Google SKU）
af_price
af_currency
price_source
fail_reason（失败时）
```

规则：

- pending/cancelled/closed/unknown/failed 分开，不用 `af_success=false` 统一代替。
- SERVICE Play 接受阶段只上报 pending，不上报 success/revenue。
- 只有 payment-service `paid + fulfilled` 后上报一次 success。
- 只有 `pay_method=google_play`、`price_source=google_play` 且 price/currency 来自 ProductDetails 时，成功事件才可带 revenue。
- catalog_quote 不推算收入。
- 恢复路径和当前购买路径使用同一订单 success 去重键。
- 不同时保留旧 Payment telemetry 和新 EventTracker 两条成功统计流。

## 13. 必须先写的测试

至少覆盖以下自动化测试，不能只测 happy path：

### Payment contract/API

- initialize body 只有 `order_id`。
- payment-service 使用独立 PAYMENT_BASE_URL。
- official 缺 SKU、错误 channel/openMode、orderId 不匹配时拒绝。
- third-party 非 HTTPS、带 user-info、expires_at 缺失/非法/已过期时拒绝。
- status 响应 orderId 不匹配时拒绝。
- 只有 paid+fulfilled 成功。
- 服务端轮询间隔和时长不能突破本地上下限。

### 订单与状态机

- 付款前持久化失败时不调用建单。
- 建单响应未知后，同商品和不同商品都不能再次建单。
- initialize 重试复用同一 order。
- 403/404/409/503 分支符合本文规则。
- `PAYMENT_CHANNEL_UNAVAILABLE` 有明确 Google SKU 时同单兜底；无 SKU 时不拿业务 product ID 查询 Play。
- active checkout 切商品不改变当前订单。
- 进程重启恢复第三方、官方 launched、awaiting fulfillment、closed、timed out。
- 每个恢复 key 首次前台会核对一次。
- status paid 但 fulfillment pending 时不成功。
- 晚到 fulfilled 能完成 timed-out/closed 原订单。
- 旧 success 延迟 ack 不能清除新支付。
- 成功只刷新一次钱包且刷新失败不降级支付状态。

### Billing

- Billing 未连接时不执行 query/launch。
- 并发购买被拒绝。
- pending 不 consume、不成功。
- backend-owned PURCHASED 不 acknowledge、不 consume、只进入 pending。
- ProductDetails quote 在 launch 前持久化。
- ownerUserId/businessOrderId 与 obfuscated IDs 不同仍能正确恢复。
- purchase token/order 优先匹配，同 SKU 歧义时不匹配。
- SharedPreferences JSON round-trip 保留 raw owner、business order、混淆 ID、token。
- Billing disconnect、进程恢复和重复回调幂等。

### Session/event/UI

- 宿主与 Core 并发刷新时，Core CAS 不覆盖宿主新会话。
- 旧 epoch 的支付响应不更新新用户。
- event 队列持久化、上限、重试次数、worker 异常恢复。
- SUCCESS 按 successDisplayMs shown/ack 并停止重启重放。
- active 支付期间商品卡 disabled。
- WebView/浏览器打开失败、返回前台和用户关闭路径。

## 15. 禁止事项

- 禁止客户端自行选 payment provider。
- 禁止 initialize 发送 order_id 之外的业务/商户字段。
- 禁止客户端根据 Play 回调本地加币。
- 禁止 backend-owned 模式 acknowledge/consume。
- 禁止只判断 `status=paid` 就成功。
- 禁止忽略 `fulfillment_status`。
- 禁止不校验 status/initialize 的 order_id。
- 禁止把 business order ID、owner user ID 与 obfuscated IDs 混用。
- 禁止进程重启后无条件重新建单或自动再次拉起付款。
- 禁止 active 支付时允许切商品并丢弃旧订单。
- 禁止用业务 base URL 拼支付路径。
- 禁止记录 token、purchase token、完整支付 URL、HTML 或原始敏感错误。
- 禁止让支付遥测失败阻塞或改变交易结果。
- 禁止复制 Core 类但让真实 UI 继续调用旧 Controller。
- 禁止伪造 platform evidence 或把侧载 APK 当作 Play 商品有效证据。
